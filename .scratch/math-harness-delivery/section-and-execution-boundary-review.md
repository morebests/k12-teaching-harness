# 旧课段职责、工具编排与模型调用的复核

日期：2026-09-16。代码基线 `2e29ec2`。本轮回答用户对旧 Section、Agent 工具职责、重复格式错误和直接模型 API 的质疑；核对现有代码、三轮真实记录和官方资料，未修改产品运行行为，也未运行新的付费模型对照。

## 1. 全年完成没有修正旧 Section

当前 `contracts.Curriculum` 仍固定 `kind=section`，其 `tasks` 保存 `prompt`、`solution`、`student_work`、`anticipated_response`、`support` 和实际内容块；`lessons` 只是 `LessonIntent`，有标题、理解转变、任务 ID 和粗时间。`rendering.py` 在学习进程后连续展开所有题目、解答及支持。这正是用户指出的层级混杂，不能因为已有全年蓝图就视为解决。

依据 [课程四层职责](../skills-harness/assets/curriculum-design-capability.md#课程与课时的双向交接)、[领域词汇](../../CONTEXT.md) 和 [文件化内容方案](content-system-design.md)，正式边界应为：

| 对象 | 应承担的内容 |
| --- | --- |
| Grade／Unit | 目标分配、顺序、时间、Narrative、进入／离开条件、评价安排和下层设计约束 |
| Section | 单元内共同完成的理解转变、表征如何推进、各 Lesson 的职责与顺序、跨课练习与检查位置、实际 Lesson 引用 |
| Lesson | 实际题面、图表、解法、预判回应、教师提问／讨论、支架、课堂时间、学生材料和学习检查 |

上层可以保留用于验证设计的代表探查及发现，教师总览可引用下层代表题；这不意味着把所有 Lesson 详情内嵌到 Section，或把学生材料、教师答案混成一页。共享题面仍应单源，由各受众视图引用，不为“分层”复制多份可编辑正文。

**具体承接：**03 先建立独立 Lesson 及师生材料契约，明确隔离旧混合 `Curriculum` 的兼容边界，不在其上继续加逐课字段；17 建立正式 Section 及实际 Lesson 引用，检查真实进程和跨课内容。旧样本和原始证据保留，不能直接补一个全年父 ID 就宣称已完成迁移；可复用任务必须重新核对目标、位置与材料，并记录采用来源。完成 03／17 后由正式结构替代旧工程路径，不能无限期同时维护两个课程模型。

当前改正尚未实现，已经写入两票的验收承接。15 的完成范围是全年蓝图；旧课段设计债仍未清偿。

## 2. 工具应由谁选择，谁执行

所有现有工具都是本地 Python 执行。`create_agent` 让模型决定何时调用哪个工具、给出什么参数，并把结果加入后续消息；它并未把本地执行交给 Gemini。因此真正要比较的是**行动选择及 Context 的控制方式**。

官方区分固定路径的 workflow 与动态选择行动的 agent；两者都可由 LangGraph 承载。直接模型调用、结构化输出和工具绑定均不以 `create_agent` 为前提。[LangGraph 官方说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

按本项目实际职责，候选分工如下；它是基于已观测缺口的设计判断，不是效果已验证的替代实现：

| 工作 | 应由程序确保的动作 | 留给模型的判断 |
| --- | --- | --- |
| 准备 | 请求核对、固定年级范围／已知父级读取、规则装配 | 未给定的课程组织及教学取舍 |
| 知识 | 已采用记录的身份与来源核验、已知查询的执行、去重及缓存、缺项反馈 | 尚不确定应深入哪个标准／关系、为何需要补查 |
| 图件与计算 | 根据已确定参数制图、参数检查、已知表达式求值 | 是否需要图、如何表征、哪些计算值得核对、解释结果 |
| 内容 | 装配当前稿与指纹，验证模型内容或局部修改，保存和渲染 | 生成数学内容、教学判断与实质修订 |
| 审阅 | 装配独立可见信息，先做确定性检查，绑定实际对象，提交结果 | 独立求解、识别教学缺陷、提出具体反例 |

“生成”和“审阅”这两个名字本身不能决定使用 Agent。输入已齐备、所需工作明确时，可以直接一次结构化模型调用；需要按内容反复查证或试做时，再保留可迭代的工具循环。业务固定动作无需等待模型决定是否执行，未知探索动作也不应硬编码成每次必查的一套清单。

## 3. 当前实现的具体问题

代码证据来自 [graph.py](../../src/teaching_harness/graph.py)、[工具定义](../../src/teaching_harness/curriculum_tools.py) 和 [middleware](../../src/teaching_harness/execution.py)。

1. `prepare_task` 已自动获取完整年级范围；`prepare_review`、`record_review` 已自动固定版本和检查。但保存、回读当前稿、图件指纹传递仍让作者决定，固定操作尚未完全收回。
2. 作者每次都暴露课段和全年两套保存工具，再在工具内部判 scope；阶段工具集尚未收窄。
3. middleware 当前只覆盖 system message，没有按当前阶段重装配 messages 或筛选工具。旧稿保留在 `request.external_content`，修订又加入当前整稿；保存参数和回读结果还会继续进入同一 Agent 的消息历史。这个 Context 设计是本项目实现选择，不是框架强制行为。
4. `prepare_review` 已发现确定性阻断时，仍无条件先调用独立审阅，之后才在 `record_review` 合并结果并回修。对于明确的格式、缺文件或来源缺项，可先修复到具备送审条件；是否合并其他教学反馈需明确权衡，不能默认每次都先消耗一次完整审阅。
5. 保存工具要求重交完整蓝图。改一个公式也会让模型重写未受影响字段，增加重复输入、输出及意外改动机会。

最后一次真实运行的 21 次工具调用为：9 次 browse、6 次整稿读取、3 次保存、3 次制图。该计数能证明实际发生的动作，不能将所有重复调用都自动认定为无用，也不能直接预测重构能减少多少 token。详见 [只读审计](evidence/agent-workflow-review/static-audit.json) 与 [原始工具记录](evidence/15-full-year-blueprint/final/tool-execution.json)。

## 4. 两类错误的责任与防复发

### 固定值约束丢失：先修工程协议

离线转换探针确认：仅有 Pydantic `Literal['grade']` 时，源 Schema 有 `const: grade`，当前转换后只剩 `type: STRING`；显式补单值 `enum` 后，转换结果保留 `enum: [grade]`。真实首次保存因 `content.id`／`content.kind` 不符被拒绝，不能解释为模型明知要求却故意忽略。

已实现：单值 enum、服务端 Pydantic 校验及供应商转换回归。尚应改进：由程序填充已知 `kind`、系统 ID、Schema 版本等元数据，模型输出契约只收它需要创作的内容；scope 只开放适用工具或输出结构。模型 Schema 和应用校验的能力不同，应用仍需验证语义；结构化输出不保证数学正确。[Gemini 结构化输出说明](https://ai.google.dev/gemini-api/docs/structured-output)

### 公式错误：提示、表示、反馈和回归一起处理

此前报告仅举了初稿一例，实际三轮都有格式问题：初稿 1 处重复转义；第二轮第一次保存返回 **18 条**重复转义错误；第三轮首次保存又有一处公式分隔符错误。规则已写单／双反斜杠区别，说明仅重复口头提醒不够。当前成功主要证明“能发现并修复”，未证明“模型不再犯”。

候选改法：

- 在实际输出 Schema 的相关字段说明和短样例中给出一致规则：LaTeX 文本命令是 `\frac`；JSON 源表示为 `"$\\frac{1}{2}$"`，解析后是 `$\frac{1}{2}$`；数组／aligned 中合法换行另行保留。示例必须从序列化往返测试产生，避免教学提示本身错一层转义。
- 程序负责 JSON 序列化和保存；不要把整份已编码 JSON 再嵌成需要模型手工重转义的字符串。输出结构内的 LaTeX 仍需解析、KaTeX 和真实页面检查，直接 JSON API 不会自动保证这些内容合法。
- 错误反馈保留位置、原片段、原因和最小正确例子；只返回需要修改的字段／对象及其依赖，程序把已校验的局部修改应用到当前源。保留重新查询依赖的能力，不以缩短 Context 丢掉必要条件。
- 对明确且不改变语义的编码问题，可研究受控规范化并记录前后差异；不能全局把双反斜杠替换成单反斜杠，以免破坏矩阵／分段函数行分隔。
- 保存本次和跨任务反例做回归，检查新任务的首次有效率、同类复发及修订是否破坏其他字段。会话内纠正不会自动训练模型；规则、Schema、校验器和反例测试才是项目可持续更新的机制。

本轮重新执行已有 Schema／内容边界测试：**17 项通过**。没有修改产品提示或渲染器，没有据此宣布防复发已经完成。

## 5. 如何验证直接模型调用是否更好

先区分三个变量：**谁选择动作、每次提供哪些 Context、通过哪个模型 adapter／API 传输**。LangChain middleware 可以逐调用覆盖 messages、工具和输出结构；掌握 Context 不要求停用 Agent。[官方 Context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)

最小有意义的对照应复用现有图、存储、知识和检查边界，只替换一个工作阶段；不是先开发第二套服务。

| 对照 | 改变 | 能回答什么 |
| --- | --- | --- |
| A：整理后的 `create_agent` | 修复共同 Schema／格式缺口，收窄工具，明确 Context；模型仍可选择探索 | 作为不故意带缺陷的 Agent 基线 |
| B：Graph 内直接结构化模型调用 | 同一模型 adapter、教学信息和校验；程序安排已知操作，需补查时保留“提出需求→执行→继续”的分支 | 固定操作与阶段 Context 是否改善质量、修订保真和执行稳定性 |
| C：原生 Gemini SDK | 在 B 的控制和 Context 已固定后，仅替换 adapter／传输路径 | 某个供应商功能、Schema、消息／缓存处理是否是 adapter 限制 |

先比较 A／B；C 仅在存在具体 adapter 限制时加入。若 A 同样受益于 Context 整理，应归因于整理，而不能归因于“不用 Agent”。若 B 仍由模型选择下一次查什么，它仍有 agent 式动态循环，只是不使用 `create_agent` 这个工厂。更换到 Interactions 是另一项 API 选择，不与以上变量一起改。

### 有限验证的输入和判据

1. 固定模型及配置、规则内容与指纹、LC 快照、学校条件、任务、旧稿、工具能力、教学检查与有效授权。比较 Context 组织时保证可取得同样的相关证据，并记录真正装入模型的内容；不能给 B 答案或额外人工帮助。
2. 第一组先用现有真实稿的局部修订和确需新增知识的有限任务，不为回答局部编排问题重新生成多份全年课程；随后随 03 的真实切片补充从零生成案例。每个条件配对重复，交错执行并记录缓存状态；少量先导样本只能筛明显失败，不能证明普遍优越或统计非劣。
3. 先看实际内容：数学／目标／来源／时间的严重错误、遗漏和误报，修订保真，完整材料要求与问题修复。相同题目的故障注入验证运行行为，不能充当自然发生概率。
4. 再看执行：首次格式通过、有效补查、重复读取／保存／制图、重试和恢复、每次实际 Context、模型／工具调用、输入／输出／缓存 token、耗时与维护负担。质量不得用更低消耗抵消；不新增累计 token 预算截断修订。
5. 匿名核读成品，保留具体缺陷与最终是否修复；没有教育评阅者时如实标为代理评价。效果相当选更简单可维护的，结果不明确就保留不确定性；不以一次成功或更短轨迹定胜负。

**当前结论：**证据足以要求清偿 Section 职责混杂，并把确定性动作和 Context 装配落实到程序；尚不足以宣称“全部改为直接 Gemini API，教学质量就更高”。下一实现应在 03 的真实材料切片中验证具体边界，保持 03→17→完整单元主线，不另起泛化架构工程。更完整的官方来源与 API 注意事项见 [配套研究](../skills-harness/assets/agent-workflow-api-comparison.md)。
