# 整体推进路径与 22 张实现票核对

日期：2026-09-16。核对基线：`27a5a52`。依据用户要求，先从教学交付反推推进路径，再检查完整 spec、22 张实现票、依赖图和拆票依据。本次没有生成课程、启动新能力实现或变更票的完成状态。

## 一、先确定要交付什么

依据 [README](../../README.md)、[完整规格](spec.md)、[课程能力决定](../skills-harness/issues/12-curriculum-design.md) 和 [现行交互基准](prototype-baseline.md)，五类教学产物分别为：

| 内容类别 | 真正要交付的内容 | 推进位置 |
| --- | --- | --- |
| 课程体系 | 全年目标与单元组织、各层设计理由、学习进程、目标／任务／评测关系，以及可交给课时设计的职责 | 主线先行；全年方案提供组织依据，单元与课段逐步展开 |
| 课时与材料 | Lesson 的实际任务、图表、解法、教师引导、学生材料和学习检查 | 将课程设计落实为能检查的教学内容，并用试做发现回修上层 |
| 教学适配 | 基于实际原课和相关学习证据的支持、支架、拓展及对应材料 | 使用已具备的原课与材料机制；保持本课目标和适用对象范围 |
| 教师备课 | 围绕真实任务与教师贡献形成的讨论、难点分析和备课便签 | 可使用外部真实原课；技术上可较早启动，不自动抢占课程主线 |
| 理解度检查 | 有诊断依据的学生题目、回应解释及教师下一步指引 | 可以从标准／焦点独立发起；不能把普通退出题当成已实现此能力 |

前两项构成当前先打通的教学主干。后三项各有独立用途与交付条件，不能当成每份教案必须依次执行的后三步。模型 API、缓存、执行图、观察、保存和渲染支撑这些工作；它们各自的技术通过不构成新的教学产物类别。

课程内容的基本关系是：**全年 Grade → 单元 Unit → 课段 Section → 课时 Lesson 与师生材料**。实际设计可以往返：用关键任务试做核对上层安排，再继续展开。全年蓝图不要求先生成全年所有教案；课程主线也不取消独立单课、外部原课备课和标准型 CFU 的入口。

## 二、基本推进路径

1. **建立真实生成入口。** 取得真实知识、装配课程设计规则，生成并保存可检查的课程方案，反馈问题并修订，服务外可以读取结果。这是首票的有限工程工作。
2. **形成真正的全年课程组织。** 遍历完整八年级 CCSS 内容与实践范围；安排单元职责、顺序、时间、复习和评测，给出 Narrative 与覆盖依据，产生目标单元的实际设计依据。
3. **落实到一课，再贯通连续三课。** 用真实上层职责形成 Lesson 和师生材料；检查数学、学生工作量、图表、受众与材料。再验证三课之间的进程、练习及评测联系，下层发现能够回到上层。
4. **完成首条教学链并扩展完整单元。** 首条链还须有适用的真实回应、检查修订和受控恢复证据；三课之后展开整个目标单元，验证跨层修改和局部支持的不同影响。
5. **扩展其余教学能力并持续比较。** 适配、备课、CFU 按所需基础接入；创建实际材料出现后即可做对应 Skills 比较，其他能力随后各自比较。完整原创单元冻结后才进行目标 IM 对照，再依据意见修订。
6. **完成生产与外部接入门槛。** 生产故障、部署、撤权、升级及五项消费者契约分别验证。它们不要求把当前教学内容工作暂停到通用基础设施全部完成，但最终发布必须同时满足相应门槛。

这是按教学价值排列的建设路径。必要质量检查随各产物完成，不能排在生成工作全部结束之后；真实人类参与也不能由合成回应替代。

## 四、查到的偏差和冲突

### 1. 首票工程边界挤占了教学主线

[拆票记录](ticket-sizing-review.md) 明确：原 01 是全年蓝图任务，后来拆为有限 01 和完整全年 15，原因是首次服务贯通与全年质量同时验收规模过大。拆分并未把全年降为远期目标；路线一直要求其后优先推进全年与单课。

因此，01 首先服务的是**课程体系设计**。当次有限课段只提供接通工程所需的样本。现在 01 已有有限闭环，下一项应接 15 形成全年课程组织，随后推进 03 与 17；不应持续扩大孤立课段，也不因对照方法被问到就把单课基线运行改为下一项内容主线。既有修复和用户明确要求的图重构有各自必要性，但不能将它们的通过当成完整教学交付。

### 2. 代表任务试做与完整 Lesson 的边界在实施中模糊

01 允许关键任务构想，课程能力决定也要求代表任务实际试做。因此，课程设计出现具体题目本身并非错误。问题是当前 [`Curriculum`](../../src/teaching_harness/contracts.py) 固定为独立 Section，集中保存题面、解答、预判回应和支持，缺少正式全年／单元与独立 Lesson。原型要求的全年→单元／课段→材料关系没有落到此实现中。

首票样本不能代替 15、03 或 17。已有结果保留为工程证据；后续应分别落实全年规划、课时成套材料和真实交接，而不是继续靠加长 Section 报告填补各层缺口。

### 3. 当前入口和首个里程碑的文档指引已过时

依赖图仍写“当前入口是 01”，没有反映已完成状态下 02、03、04、15 均已满足代码前置，而**教学价值排序应优先 15**。同段把 18 也放入“这些一起组成首个教学交付里程碑”，与当前完整故障恢复后置的阶段约定冲突。

本次更新执行指引：已完成的 01 保留身份；当前下一内容任务是 15，其后 03、17；02／16 和相应基本运行行为补齐首条链，18 的完整故障矩阵不作其前置。没有改动 38 条工程硬依赖。

### 4. 文件化阶段尚未逐票落实

02 验收仍有“采纳动作和待续作标记在业务事务内提交”及“持久动作／待续作事务仍必须在本票实现”；04 仍写“业务数据库仍是权威状态”；03、15、17 等保留不可变引用／具体版本的交接表述。规格开头已经明确当前无业务数据库、无内容历史、原生框架保存状态，但只写总括覆盖容易在下一票重新引入已后置工程。

这些是**进入相应票前需要按现行阶段收口的条款**，不应默默按旧全文建设：02 用原生检查点和 interrupt／resume 落实真实回应及受控恢复；04 关联当前框架状态和内容／检查；内容交接保存本次实际输入与指纹、检查适用性，不宣称指纹可回取任意历史版本。生产事务与完整历史保证继续保留在相应后续范围。本次只记录冲突，不把未实现的新机制记为完成。

### 5. 业务操作语义与旧 HTTP 命名容易混淆

spec 的 `/v1/tasks` 表仍像当前必建接口，而阶段约定已经采用 Agent Server 原生 API／SDK。六类操作的教学语义仍有价值，旧路径命名不能成为重新自建一套任务服务的依据。本次在表前明确当前适用口径；具体行为随票交付，不新增空接口。

### 6. 对照需要前移，但不能替代尚不存在的教学产物

11 依赖 03，明确比较已实现的完整单课直接生成路径；12 依赖完整单元和评价入口；19 汇总四能力。现有依赖合理地区分早期反馈与完整比较。上一轮准备单课 brief 回应了用户的方法问题，但必须说明它是准备工作，当前产品没有对应 Lesson，不能借此继续绕过全年主线或给 Section 与 Lesson 排名。

## 五、当前执行结论

**第一优先内容是课程体系；当前应从已完成的 01 接续 15，形成真实全年蓝图。** 这落实既有拆票后的主线，不把票号误作执行顺序，也不把全年逐课材料、单课全部流程和生产保障重新塞入 01。

随后以实际目标单元开展 03 的一课材料生成，再通过 17 完成正式课段与连续三课交接。03 保留独立课时接口，但本项目的主线验证应优先使用实际全年方案提供的上下文。必要 HITL、检查和受控恢复随首条链补齐；适配、备课、CFU、Skills 对照与生产分支按上表进入，不抢占尚未实现的全年内容。

本次更正的是排程指引和文档适用口径，没有宣布全年、Lesson 或 A/B 已实现，也没有替用户新增生成任务。下一票的实际数据范围、当前格式扩展和教学验收应在该票内落实，不再先建设一个通用内容平台。
