## 结论

**核心结论：检查器现在能较可靠地发现明显问题，但还不能可靠地判断问题有多严重、方案有多好。人工校准之前，模型给出的维度分和严重度不能作为放行或比较的依据；23 尚未完成。**

| 能力 | 证据（第二版盲设保留集：10 个注入问题、4 个合法对照，人工逐条核对） |
| --- | --- |
| 发现问题：组合使用时较可靠 | 程序检查加专项检查，再加任一模型评阅，检出 9/10（Gemini）或 10/10（DeepSeek），对照零误报。但单一模型从 7/10 到 10/10 不等，焦点单元不一致只有 DeepSeek 发现，所以要靠程序与两个不同模型的组合 |

## 怎样设计，为什么

**尺度只有一份。** 维度、权重、锚点与裁定规则都从 [规则数据](../../year-planning-rubric.json)读取。读取时与 [评估协议](../../year-planning-evaluation.md)第 4 节的权重表互相核对，任一处改动不一致即拒绝。评分记录类型覆盖规则数据要求的全部字段。

**冻结在先。** 配置记录规则、协议、评价条件、评阅与修订规则、专项规则、评阅装配与检查代码（v2 起）、调试样本与答案、各保留集目录、抽取清单和 IM 来源的指纹。保留样本、裁定和修订运行前核对这些指纹，还核对所选保留样本是否列在该配置中；calibrate 与程序检查不处理未列入冻结配置的保留集。配置同时记录证据范围、参考接触清单、各检查的输入与排除项，以及局限。

**证据分层。** 每条证据保存来源文件指纹、JSON Pointer 或字符区间、原文片段和不补写的提取；判断写在对象结论或发现里。核验时分别报告快照缺失、文件改变、位置失效与原文不符。

**对象级核查。** 每维有应查对象清单。Q1 按完整来源范围列出 36 项目标与 8 项实践，不按候选自报。Q7 按每个单元、每个探查和教师准备逐项核对资源。以下情况都进入汇总状态，既不计零，也不算通过：分数与对象结论矛盾、覆盖未完、引用失效、只有一位评阅、不可观察、不可比、评分不一致、评分高于已确认发现的上限。

**独立评阅的输入。** 每次评阅只装配以下内容：

- 按稳定身份呈现的候选；
- 15 初稿请求中的原始任务与合成学校条件；
- 年级标准与数学实践原文；
- 公开判据和应查对象。

不含作者对话、15 的 `checks.json` 与 `context.json`、修订请求与旧稿、另一评阅者结论、样本改动与答案、IM 材料。每次调用前程序核对输入中不含答案说明（`assert_isolated`），专项检查与修订调用也一样。模型按单元编号、目标代码、探查编号和“单元:角色”定位，由程序换算回下标；引用失效或漏交时，在同一会话中补交一次。

**跨模型评阅。** r1、r2 是同一模型（`gemini-3.8-flash`）的两次独立调用，只能测出同一模型的采样波动。rd 用 `deepseek-flash`，规则、输入包、输出结构、引文核验与补交都与 r1、r2 相同，只换模型。调用条件有三处差异：

- DeepSeek 的思考模式不接受强制工具调用，改由模型自行调用结构化结果工具，没有提交时这次调用记为失败；
- 接口不回传上一轮的思考内容；
- 输出上限不同：第二版保留集首轮为 32,768，终稿与补跑为 131,072。

Gemini 同样开着思考模式，工具调用由调用方强制。两家都自动缓存相同的请求开头，不需要传参数。

**专项检查：让程序接手能核对的部分。** 第一阶段系统性漏掉的问题，不靠加严整体评阅的提示来弥补，而是交给三项窄检查。

- **承诺核查**：模型只从叙述中抽取后续利用、评价、依赖、课时分项与总数五类承诺，逐字引用出处；位置、先后与合计由程序核对。
  - 机动合计只按机动计划本身列出的分项计算，别处提到的机动课时视为引用。
  - “同一批课时同时计入单元与机动”完全取决于模型对原文的归类，记为模型发现。
- **探查核查**：先只给题面、表格、图件参数和学校条件，独立求解。
  - 程序再算出各表格列的取值范围、文中区间表述、与数据列重叠却超出其范围的区间、只有下界的区间，以及正文提到却没有提供的图或表。
  - 核查者须逐条回应独立解答的每一问、每个条件、每项缺失信息和每条程序事实；判为影响结论的项须链接到具体发现，不完整时补交一次。
  - 同一模型对同一题面、条件、程序事实与规则的输出在样本间复用。
- **数学表述核查**：只读叙述性字段与目标分配，每条发现先归入五类错误，严重度不超过该类上限。只有“在所述条件下结论本身为假”的关键结论可以是重大失败。

**已确认发现限制评分。** 程序检查和专项检查得出、引文经原文核实、未被驳回的发现称为已确认发现。它们按协议限制维度分：重大失败为 0，关键缺口最高 2。

- 评分高于上限时，该维记为冲突，不出总分，也不参与比较，交给裁定。
- 裁定逐条维持或驳回，驳回须引用可核实的原文；程序核对的结构事实不能由裁定驳回。
- 已确认的重大失败不等裁定就触发整体重大问题标记。

专项检查中的模型发现只经过一次模型判断，因此它们对评分的限制，要经过裁定这一次复核才会生效。

**检出统计。** 一条发现只计入一个预期问题。先求检出最多的分配，再让位置正确、严重度一致的最多（最小费用最大流）。答案关键词和位置匹配仍是近似判定，本报告的检出数都经人工核对。

## 证据索引：本项目与 IM 的输入契约

`im_snapshot.py` 取得 IM 八年级全年页、9 个单元总页和评价指导的公开正文，没有登录。全文只存在本机 `work/grade-evaluation/im/`，[来源清单](im-sources.json)记录 URL、日期与指纹。IM 6–8 Math v.360 按 CC BY-NC 4.0 授权，[抽取清单](extractions.json)只保存短摘录与出处。节奏图与依赖图是图片，经 [来源核查](../../comparisons/im-grade8-scope-and-sequence-source-review.md)人工转录后作为部分来源登记。

- **核验**：25 条证据全部通过。其中 IM 19 条，覆盖 9 个单元、依赖含义与箭头、三类评价、节奏与天数口径；本项目终稿 6 条。
- **抽查**：23 条提取如实。另有两条有意保留的不忠实样例：一条把“存在 8.3→8.6 箭头”补写成“唯一必要先修”；一条把 `apply` 写成“再次应用”，混入了判断。
- **不可观察的 4 项**：
  - IM 单元总页没有标准代码对齐，Q1 逐项核查需要课时页或登录材料；
  - Section Checkpoint 需要登录；
  - 节奏天数没有分钟数，不能与 50 分钟课时换算；
  - 依赖图全文只有人工转录。
- 本票不对 IM 评分；同尺度比较由 26 承担。

## 校准样本

所有注入与对照都在 15 终稿副本上按记录的改动生成，改动后仍须是合法的年级课程。答案写明以下内容：

- 位置与可接受的维度、对象；
- 严重度；
- 应由程序还是模型发现；
- 用于区分同一位置不同问题的关键词。

**第一版保留集不是盲设的。** 它由规则作者在写完 v1 规则之后设计，v1 已含与部分变体直接对应的句子，原文见 [rules-history](rules-history/grade-review-v1.md)，指纹 `6927f1f0f433`。开发专项检查时又逐条查看了它的结果，所以它现在只能当作开发样本。

**第二版保留集的设计与隔离。** 设计子代理的读取范围：

- **读了**：协议、判据、终稿、学校条件、标准原文、`CONTEXT.md`、`contracts.py` 与 `calibration.py`；
- **没读**：评阅规则、程序检查与专项检查实现、旧样本和工单。

它先在全文中检索，确认“遗漏”类对象没有别处分担，再为八个维度都安排了样本；它自己的 [设计说明](holdout-2/design-notes.md)有记录。因为读过检出匹配代码，它有意把答案位置写得较宽，这可能抬高位置正确率。

## 怎样重跑与核对

需要 `uv sync --frozen`，并在 `.env` 中配置 `GEMINI_API_KEY`；跨模型对照还需要 `DEEPSEEK_API_KEY`。程序检查、索引、汇总、核验、承诺重判与报告不调用模型；`review`、`stages`、`adjudicate`、`revise` 调用 Gemini（rd 调用 DeepSeek）并产生费用。LangSmith 不需要在线。

```bash
uv run python .scratch/math-harness-delivery/evidence/23-grade-evaluation/im_snapshot.py
uv run python scripts/evaluate_grade.py materialize
uv run python scripts/evaluate_grade.py program
uv run python scripts/evaluate_grade.py index
uv run python scripts/evaluate_grade.py freeze --draft config-draft-v4.json --holdout-sets ""
uv run python scripts/evaluate_grade.py review --reviewer r1 --split all
uv run python scripts/evaluate_grade.py review --reviewer r2 --split all
uv run python scripts/evaluate_grade.py review --reviewer rd --model deepseek-flash --split holdout-v2
uv run python scripts/evaluate_grade.py review --reviewer rd --model deepseek-flash --split holdout-v2 --retry-failed
uv run python scripts/evaluate_grade.py review --reviewer rd --model deepseek-flash --split all --only b-final
uv run python scripts/evaluate_grade.py stages --stage all --split all --repeat 3
uv run python scripts/evaluate_grade.py stages --split all --recheck
uv run python scripts/evaluate_grade.py calibrate
uv run python scripts/evaluate_grade.py adjudicate --candidate b-final
uv run python scripts/evaluate_grade.py adjudicate --candidate d-known-initial
uv run python scripts/evaluate_grade.py summarize --candidates b-final,d-known-initial --reviewers r1,r2
uv run python scripts/evaluate_grade.py revise --candidate b-final --reviewer r1 --finding model:r1:b-final:q8:1
uv run python scripts/evaluate_grade.py revise --candidate b-final --reviewer constructed --finding human:constructed:b-final:q7:stale-resource --finding-file .scratch/math-harness-delivery/evidence/23-grade-evaluation/results/revision/constructed-stale-resource.json
uv run python scripts/evaluate_grade.py verify
uv run python scripts/evaluate_grade.py usage
uv run python scripts/evaluate_grade.py report
```

说明：

- `freeze` 会重写当前配置，只在建立新配置版本时运行；旧版本另存为 `config-v1.json` 至 `config-v3.2.json`。
- v4 起 `summarize`、`adjudicate` 默认使用 r1 与 rd；上面的 v3 结果用 `--reviewers r1,r2` 复算。
- v4 下尚未运行任何模型。正式运行前，先以正式设置做覆盖全部维度组的冒烟测试，记录失败诊断，估算费用与时间，经确认后再运行。
- 已有结果会被跳过。专项检查中失败的运行，以及规则或模型已变的运行，再次运行时自动重跑，被替代的运行移入 `stages/<检查>/history/`，用量仍计入；汇总与校准只采用按当前规则和模型产生的运行。`stages --force` 全部重跑，`stages --recheck` 只按已保存的承诺抽取重新判定。`revise` 已有结果时只按保存的复查重算发现状态。
- 冻结内容改变后，保留样本评阅、专项检查、裁定和修订都会被拒绝，必须另建配置版本。
- 第二版保留集的整体评阅、承诺抽取与表述核查在 v2 代码下运行。v2 到 v3 的代码差异不改变这些调用的模型输入：
  - `review.py` 只改了裁定；
  - `stages.py` 对这两项只改了程序判定与拒收处理，本次运行没有出现拒收；
  - 承诺判定已按 v3 离线重算，探查核查已在 v3 下重跑。

逐条核对一次评阅：

```bash
uv run python scripts/evaluate_grade.py show --reviewer r1 --sample h2-10
```

它列出每维分数与理由、非“有依据”的对象、每条发现及其原文位置、失效引用，并与答案对照；加 `--all` 同时列出“有依据”的对象。模型实际收到的输入和原样返回保存在本机：

- 专项检查：`work/grade-evaluation/transcripts/stages/`

## 局限

- 没有专业评阅校准；同一模型的两次调用既无法互相证明可靠，也可能共享盲点。
- 第二版保留集只有 10 个注入问题、4 个对照，而且由与实施者同类的模型设计；数量和来源都不足以估计一般检出率。
- 维度分随评阅模型系统性偏移；rd 是结果已知后追加的对照评阅者，只跑了一次，调用条件与 Gemini 有三处差异（见“怎样设计”）。
- 探查与表述核查存在明显的运行间波动，未做重复运行的方差估计；上文各轮数字只代表各自那一次运行。
- “已确认发现”包括只经一次模型判断的专项发现，它们要经过裁定才会最终限制分数；裁定目前不能调整严重度。
- 探查程序事实不报告完全落在数据之外的区间和点预测；图件绘制参数随题面交给独立求解，图文不一致可能看不出来。
- 注入样本、答案、关键词和对照由模型构造；自动匹配会出现关键词误命中，检出数以人工核对为准。
- 学校条件是合成条件；课时与资源判断不代表真实学校。

## 工程验证与代码审查

测试覆盖事先确认的六个边界，专项检查归入模型评阅适配的边界（见 [测试说明](../../../../docs/testing.md)）。全套测试、Ruff、mypy 与契约导出的结果见票的完成评论。

**第一阶段的双轴审查**：主要意见均已修正。

- **规范轴**：补上运行记录类型；汇总核对评阅规则；程序发现改用内容身份；缺失用量标为不完整；消除重复代码与字符串标记。
- **规格轴**：补全重跑清单；裁定与修订核对冻结状态；复查后才关闭发现；裁定保留失效依据。

**v2 冻结后的双轴审查**：在查看第二版保留集任何模型结果之前完成，修正后冻结为 v3。

- **汇总与裁定**：
  - 冲突维度不再参与比较；
  - 已确认重大发现触发整体标记；
  - 程序核对的结构事实不能由裁定驳回。
- **专项检查**：
  - 承诺缺少单元时记为不可核对，不再中断核查；
  - 层级写成 1、2 以外的值时按细分处理；
  - 同时计入两处的判断记为模型发现；
  - 对象身份无效的一条发现只拒收它自己；
  - 链接到被拒收发现的核对项留下问题记录；
  - 修正“10 ≥ x ≥ 0”、“x ≥ 0 且 x ≤ 8”、“代表中”的识别；
  - 探查缓存键加入模型与程序事实。
- **检出匹配**：在检出最多的前提下，位置正确的发现优先。
- **本地命令**：
  - `--recheck` 不调用模型，并保留新旧问题记录；
  - 阶段名校验；
  - 探查规则分开读取，不再按标题拆分；
  - 冻结保护扩展到所选样本、calibrate 的全部统计和程序检查。
- **未修改的项**：
  - 完全落在数据之外的区间：没有可靠方法把这类表述对应到某一数据列，由核查规则负责；
  - 规则文本中“全年”的旧用法：修改规则须重评，随 24 统一；
  - 已确认发现的范围：改为在报告和配置中写明其含义，由裁定复核；
  - `cli.py` 体量较大、`_figures` 与探查查找有重复：不影响行为，留待 24 调整结构时处理。
