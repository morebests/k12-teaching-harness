## 为什么这样组织原型

先显示真实的任务内容，再显示状态。演示片段先让学生比较不同图形，接着自行构造并检验三角形，阶段评测保留同一要求。任务、课时和时长均为自编模拟，目标背景来自已有 [几何知识研究](learning-commons-integration.md)；未查询新的 LC 数据，不构成完整单元或首个实施主题。

把下列信息分开，分别观察变化：

- **内容快照与采用对象**：U1 原始课程、后续候选、当前已采用课程及个人适配 P2。旧快照可回取，个人支持不会改写全体课程。
- **检查结果及其依据**：数学题面、学习机会与评测、时间容量、Narrative、学生页版式、依赖影响范围各自保存结果；只对本次输入仍相同的检查复用。
- **实际展示与回应**：请求保存展示版本，回应保留原文、模拟参与者、事件身份及处理结果。内容接受和允许继续生成分别记录。
- **工作与交付**：计算是否停止、是否缺决定、剩余额度、未完成检查和旧交付可以同时存在。旧包可用并不等于新修改已完成。

纯逻辑使用一个限定案例的 reducer；页面只负责展示和发动作。预设检查函数通过案例字段返回发现，固定按钮代表已解释的模拟自然语言事件。没有实现通用课程语义判断、通用权限系统或所有能力的状态机；不将这份 HTML 直接搬进生产系统。

## 场景对应的真实使用情况

用户提出：“老师的交互也是这个样子的？单单记住这几十个场景点就很难。”这暴露出原型的定位说明不足。**这里的编号是开发者走查入口，不是教师功能菜单；步骤按钮同时模拟模型、程序与人类动作，不能直接交给教师逐步操作。** 已将页面标题和每个场景的说明改清。

| 场景 | 现实中的触发 | 人类实际需要做什么 |
| --- | --- | --- |
| 删课与容量 | 课程负责人要求减少课时且目标不变 | Harness 先尝试重排，确实冲突后才由有权者决定时间／范围取舍 |
| 描轮廓的陷阱 | 教师建议将自主作图换成更省事的描线 | 理解目标会失去什么；目标内可修复的由系统修复，目标变更才需相应决定 |
| 只改作图区 | 教师在已要求的草稿审阅中提出扩大空间 | 提出修改；任务决定仍有效时不重问相同任务，系统重查页面 |
| 只改／改后生成 | “先改给我看”和“改好直接生成” | 正常表达后续意图，不选择内部状态 |
| 单个学习者 | 外部已有学习证据更新支持需要 | 按需要提供／审阅支持意见；证据采用、影响范围和检查由系统承载 |
| 旧版与重复 | 旧页面的回复迟到，或网络重传相同提交 | 通常无额外操作；旧决定确实不适用时，只针对当前具体差异回应 |
| 多人规则缺失 | 外部尚未确定谁对这次结果作决定 | 外部产品向负责人／管理员补齐责任；不是让教师研究事件优先级 |
| 共同决定冲突 | 已有责任规则下，有权协作者给出相反意见 | 围绕争议内容按既定责任解决；系统保存意见并暂停相关放行 |
| 依赖未知 | 本课程建立的跨课依赖记录不完整 | 系统先读取知识依据及实际课程补查；不能把技术缺口转成教师问卷 |
| 耗尽与迟到 | 本次生成计算额度耗尽后，旧回应才到达 | 看见已完成、未完成与后续选项；额度与恢复遵守外部配置／授权 |
| 取消后回应 | 用户取消，之后旧回应才送达 | 用户只需取消本次工作；系统阻止旧回复重新启动它 |

实施时应围绕对象范围、实际改动、检查依据、有效人类决定和执行条件组织机制；用这些场景检验机制的组合行为，而非要求教师选择场景编号或穷举每一种表达。五项能力仍保留各自流程，尤其不能把备课中的教师亲做当作可以隐藏的系统检查。外部产品负责教师界面；Harness 的接口必须返回足够具体的教学问题和结果，让界面能够隐藏内部步骤而不丢失必要的人类参与。

## 已运行的场景

运行环境：Node `v26.8.1`。读取 HTML 的 `logic` 脚本和引导场景声明，逐步调用同一状态函数；另对两段 JavaScript 做语法编译检查。没有新增测试框架或持久化测试套件。

| 场景 | 实际观察 |
| --- | --- |
| 删课与容量 | 删除 L2 后缺构造机会；移入 L1 后出现 30 分钟任务／20 分钟容量冲突；取得模拟明确加时授权、同步叙述并检查后交付 U5，保留 U1 |
| 描轮廓的陷阱 | 题面没有数学事实错误，但构造机会与 Narrative 检查失败；拒绝交付，恢复自行构造后可继续 |
| 只改作图区 | U1 的任务决定可以适用于 U2；新版式未检查时拒绝交付，检查后交付 U2；没有生成“已审 U2 页面”的事实 |
| 只改／改后生成 | “只修改”后仍等；明确“改好直接生成”后可继续，未再次改变的内容不产生空修订；没有内容接受记录 |
| 单个学习者 | E2 到达时仍采用 E1；明确采用后生成 P2，个人检查前拒绝交付；最终课程基线仍是 U1 |
| 旧版与重复 | 旧 U1 同意不批准改成描轮廓的 U2；已采纳事件重传不增加决定；相同 ID 不同内容拒绝覆盖；新事件中的改意暂停生成 |
| 多人规则缺失 | 收到甲乙两次同意仍等待外部决定规则；没有按先到者放行 |
| 共同决定冲突 | 一方同意不足以放行，另一方反对后保留冲突并拒绝交付 |
| 依赖未知 | 未知影响阻止交付；补查依据更新后仍需取得该依据上的检查，不能只切回“完整”标记复用旧通过 |
| 耗尽与迟到 | 冻结未完成 U2，保留 U1 旧交付；迟到回应不恢复计算或预算，版式仍待查 |
| 取消后回应 | 保留取消事实及迟到回应；不恢复生成，不抹掉历史交付 |

另外实际运行了七组自由组合：接受新的语义版本后只改版式；共同同意后有人反对；反对者再改为同意；补查后跳过重查尝试交付；已采纳回应和交付的重复；已查页面再改成描轮廓；等待时尝试启动检查。对应阻止／继续行为与当前设计相符，其中等待时检查未扣除演示预算。

## 实现原型时暴露的问题

**检查适用性必须包含所依据的证据。** 第一版用一个“依赖完整”布尔值，发现缺失再补查后可能匹配回初始通过。已改为同时关联本例补查依据 I1／I2／I3。生产接口需要表达来源、规则、覆盖范围与输入版本，不能仅存“已检查”或内容哈希。

**历史接受不能永久要求当前重新确认。** 第一版扫描所有旧接受记录，会把“旧语义已失效、当前新语义已重新接受、此后只改版式”也误判为需要再问。已改为比较本次改变前适用的决定与本次实际变化，保留历史而不让它产生无期限的等待。

**多人意见可以在一次回应之后改变。** 共同同意后再出现反对，必须暂停对象并使该共同决定不再作为有效放行依据；反对者再次明确同意时，也要能按既定共同规则形成新决定。已运行这两种顺序，不能只在第一次回复时检查人数。

**停止与未满足条件在页面上也要分开。** 页面走查发现取消后顶部已显示停止，人类区仍显示等待，容易让人误以为回复能恢复运行。已改成明确“本轮已停止，保留未满足条件”；已交付范围、等待另一位决定者、等待外部责任规则也分别呈现，修正后实际点击复查。

这些修正支持 [执行结构](execution-structure-design.md) 和 [HITL 设计](hitl-design.md) 的语义方向，尚不足以确定生产字段、并发事务、权限实现或存储结构。

## 后续工作如何读取本结果

[调用接口](../issues/02-execution-interface.md) 可以据此提出具体输入输出：课程候选及采用版本、检查依据、原始回应及适用范围、个人支持采用证据、交付与未完成事项。接口应能解释当前为什么停下，而不只暴露一个 approved／done。人类行为反馈可能调整这些表达，当前不把原型字段定为正式契约。

[质量验证](../issues/05-capability-validation.md) 要用实际新旧任务检验 LLM 能否发现描轮廓降低认知要求、删课导致机会缺失、调整后邻课无法容纳等问题。这里的预设发现不能作为模型成绩，也没有证明与原 Skills 相当或更优。

[CFU 运行原型](../issues/09-cfu-runtime-prototype.md) 与 [完整运行时专项](../issues/11-agent-server-stack-research.md) 再验证真实暂停、重启、竞争回应、在途结果、预算与副作用。浏览器内存或 Node 顺序执行不证明服务器可靠。

后续讨论针对真实教学需要和具体行为，例如“只改作图区仍沿用任务决定”“依赖补查后仍须重查”；不要求记忆场景编号或批准抽象状态名。原型依用户保留研究参考的要求在当前本地路径保留，作为一次性证据链接进入规格；不迁入生产代码，也不以归档操作中断主线。
